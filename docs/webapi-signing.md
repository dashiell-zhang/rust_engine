# WebAPI 请求签名

管理端声明了签名要求的接口在 Release 构建中验证签名。Debug 构建跳过该步骤；`APP_ENVIRONMENT` 不决定是否启用签名。普通文件上传接口保留签名要求，Ueditor 只执行认证与权限校验。

受保护端点先完成认证、续签与权限检查，再绑定和验证处理器参数，之后运行签名等 Action 过滤器。Query 或 JSON 模型验证失败时直接返回参数错误，不继续检查签名；未认证请求仍先返回认证失败。

请求头包括 `Authorization: Bearer <JWT>`、Unix 毫秒时间 `Time` 和大写十六进制摘要 `Token`。计算方式为：

`Token = SHA256(JWT 的编码签名段 + Time 原文 + 请求路径与查询串 + 签名请求体)`

字符串按 UTF-8 编码，摘要输出为大写十六进制。Time 加三分钟必须晚于服务端当前时间。使用登录返回的完整 JWT；是否需要认证由接口本身决定，签名不替代认证。

路径使用请求路径与查询串的 URI 表示：先按宿主规则解码一次路径并消除 `.`/`..` 段，再转义不允许直接出现在 URI 中的字符，查询串保持原文。`/Us%65r/GetUserList?x=%41` 参与签名的是 `/User/GetUserList?x=%41`，不能把查询串改成 `x=A`，也不能用路由登记的大小写替换实际路径。编码斜杠 `%2F` 保留原编码及十六进制大小写；路径中的 `+` 不作为空格。详细规则见[请求路径说明](webapi-network.md#请求路径表示)。

- JSON 或文本：使用请求体文本；gzip 按解压后的文本计算，按 BOM 识别 UTF-8、UTF-16 或 UTF-32。
- URL 编码表单：按字段名排序，依次拼接字段名和值；字段名按 OrdinalIgnoreCase 合并，保留首次拼写。同名字段的非空值按出现顺序用逗号连接，空字符串不增加分隔符，空白字符串仍保留。
- multipart：先按上述规则处理普通字段，再按文件字段名排序，拼接每个文件的字段名和该文件内容的 SHA-256 大写十六进制摘要。文件名不参与摘要，多个文件分别计算。

表单绑定、签名及参数快照共用 Content-Disposition 解析。参数名不区分大小写，优先选择可解码的 `filename*`，再选择 `filename`；两者均为空时按普通字段处理，包括 `filename=""`。`name` 保留原始大小写，普通字段与文件各自参与签名。只读取 `form-data` disposition 类型，其他合法 disposition 不作为表单字段。

字段名与文件字段名采用宿主文化的稳定排序，排序等价时保留提交顺序，不使用字节顺序。Linux 宿主依次读取 `LC_ALL`、`LC_MESSAGES`、`LANG`，未设置、空值及 C/POSIX 使用 invariant 文化；支持 BCP 47 名称及 `sv_SE.UTF-8` 这类无 `@` 修饰符的 POSIX 名称。签名端应使用相同文化规则，不能仅把字段转小写再排序。目前带 `@` 的 POSIX 文化修饰符尚未支持。

参数绑定和签名验证共用按需填充的请求体缓存，各读取流拥有独立偏移。实际读取内容不超过 30 KiB 时保存在内存，超过后使用容器中的匿名临时文件；文件内容逐块计算摘要，流式上传处理器仍可读取完整原文。缓存随最后一个回放句柄释放而回收。可通过 `ASPNETCORE_TEMP` 指定临时目录，未设置时使用系统临时目录；指定目录必须已存在且可写。读取或缓存失败通过共享内部异常响应处理。

文本及普通表单需要完整解码为字符串，不能套用文件上传的内存占用特点。普通文件上传不添加额外的固定大小上限，反向代理和部署环境仍可以配置自己的限制。

## JSON 请求示例

假设请求路径为 `/Example/Save?id=1`，发送正文为 `{"name":"demo"}`，签名原文为：

```text
<JWT第三段><Time原文>/Example/Save?id=1{"name":"demo"}
```

对该文本按 UTF-8 计算 SHA-256，转成大写十六进制后写入 Token 头；同时发送同一 JWT 和同一 Time。正文中的空格、字段顺序及查询串编码都应与签名时一致。

Rust 调用端可直接使用 [HttpSign 命名客户端](http-client.md#签名客户端配置)完成令牌获取与签名。
